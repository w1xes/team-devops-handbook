# Гілки, коміти й чиста історія

Відповідальний: @w1xes.

## Гілки та PR

Основна гілка — `main`. Одна завершена тема — одна гілка
`feature/w1xes-<тема>` і один PR. Наприклад:
`feature/w1xes-readme-template`. Документацію також змінюємо через PR.

```sh
git switch main
git pull --ff-only
git switch -c feature/w1xes-readme-template
```

Робочі коміти мають пояснювати окремі зміни. Після рев'ю додаємо новий коміт,
а не робимо amend/rebase/force-push. Так коментарі лишаються прив'язаними
до перевіреної версії. До нового коміту додаємо посилання у відповідь рецензенту;
автор закриває обговорення лише після виправлення чи аргументованої відмови.

## Формат Conventional Commits

```text
<type>[(scope)][!]: <опис>

[пояснення причини та наслідків]
```

Дозволені типи: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert`. `scope` необов'язковий: малі латинські літери,
цифри, `/` і `-`, перший символ — літера. Заголовок до 72 символів Unicode,
без кінцевих пробілів; тіло відділене порожнім рядком. `!` позначає несумісну
зміну. Опис формулюємо конкретно, українською або англійською.

| Приймається | Відхиляється | Причина |
| --- | --- | --- |
| `docs: document curl exit codes` | `fix2` | немає типу й опису |
| `fix(hooks): reject trailing spaces` | `Fix: hooks` | тип має бути малими літерами |
| `feat(cli)!: require explicit output path` | `feat:` | порожній опис |
| `test: cover failed HTTP responses` | `wip: try again` | немає дозволеного типу |

## Встановлення й перевірка хуків

```sh
sh scripts/install-hooks.sh
git config --local --get core.hooksPath
python3 -m unittest discover -s tests -v
```

Скрипт виставляє локальний `core.hooksPath=.githooks`; повторний запуск безпечний.
Інший уже налаштований шлях він не перезаписує. Тека `.git/hooks` не
версіонується, тому після клону встановлення треба повторити. Збережені
`.githooks/pre-commit` і `.githooks/commit-msg` мають виконуваний біт.

`pre-commit` запускає `git diff --cached --check`, перевіряючи лише індекс.
`commit-msg` перевіряє повідомлення Python-скриптом. Хук `pre-commit` ще не має
готового повідомлення, тому перевірка повідомлення належить саме `commit-msg`.
`--no-verify` обходить локальні хуки; CI повторює перевірку на сервері.

## Squash і список змін

У PR зберігаємо тематичні робочі та виправні коміти. Під час злиття обираємо
**Squash and merge**, а заголовок результуючого коміту перевіряємо за тією самою
конвенцією. Це дає один змістовний коміт на PR у `main`, не приховуючи
послідовність виправлень у самому PR. Початковий порожній коміт створює базу
для першого PR у порожньому репозиторії й не містить змін довідника.

```sh
git log --oneline main
python3 scripts/changelog.py --output CHANGELOG.md
python3 scripts/changelog.py --since <commit-or-tag> --output CHANGELOG.md
```

Генератор не змінює Git-історію: групує Conventional Commits, показує їхні
короткі SHA та позначає breaking changes. `--since` виключає вказану ревізію;
без нього включається вся історія. Для історії `main` спочатку перемкніться
на `main`. Не підставляйте недовірені shell-вирази замість ревізії.
