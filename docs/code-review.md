# Чек-лист рецензування консольних утиліт

Відповідальний: @w1xes. Для кожного пункту рецензент ставить «так», «ні» або
«не застосовується» з поясненням. Пункт «ні» перетворюється на конкретний
коментар із відтворенням, очікуваною поведінкою та місцем у diff.

## Інтерфейс і запуск

- [ ] Чи працює мінімальна команда з README на заявленій версії без прихованих файлів автора?
- [ ] Чи `--help` пояснює кожен підтримуваний прапорець і завершується кодом 0?
- [ ] Чи невідомий прапорець або відсутній обов'язковий аргумент дає ненульовий код і повідомлення в stderr?
- [ ] Чи позиційні шляхи з пробілами передаються одним аргументом, а ім'я з `-` підтримує задокументований `--` або безпечний аналог?
- [ ] Чи явно описано взаємовиключні опції, типові значення й пріоритет CLI/змінних/конфігурації?

## Потоки, результати й файли

- [ ] Чи stdout містить лише заявлений результат, а діагностика й прогрес ідуть у stderr?
- [ ] Чи документований код 0 відповідає потрібному успіху, а не лише вдалому транспорту?
- [ ] Чи коди для невірного вводу, недоступного файла й мережевої помилки перевірено окремо?
- [ ] Чи порожній stdin і EOF обробляються за контрактом без зависання?
- [ ] Чи відсутній файл і заборона запису дають ненульовий код, зберігаючи наявні дані?
- [ ] Чи перезапис файла вимагає явної згоди або чітко задокументований як побічний ефект?
- [ ] Чи тимчасові файли очищаються після успіху, помилки й переривання, не видаляючи чужих даних?

## Мережа й безпека

- [ ] Чи мережеві запити мають задокументовані таймаути, а повтори обмежені й безпечні для операції?
- [ ] Чи збережено перевірку TLS та перевірки цілісності завантажень?
- [ ] Чи секрети відсутні в diff, URL, прикладах команд, stdout/stderr і тестових знімках?
- [ ] Чи недовірений ввід передається як аргумент процесу, без `eval` або складання shell-команди з вводу?
- [ ] Чи немає несподіваних записів поза обраною текою або вимоги зайвих прав адміністратора?

## Перевірки й документація

- [ ] Чи тести реально виконали успішний і щонайменше один помилковий сценарій із перевіркою кодів і потоків?
- [ ] Чи приклад README відтворено на реальному інструменті, а його версію й обмеження записано?
- [ ] Чи `.editorconfig` має очікувані ефективні значення після злиття, а не лише коректний синтаксис?
- [ ] Чи `.gitignore` приховує згенеровані артефакти, зберігаючи джерельні файли й шаблон `.env.example`?
- [ ] Чи CI пройшов на поточному HEAD, а обговорення закрито після виправлення чи аргументованої відмови?

## Змістовний коментар і відповідь

Приклад: «README обіцяє ненульовий код для HTTP 404, але команда без
`--fail-with-body` повертає 0. Додайте прапорець і перевірте обидва варіанти».
Це перевіряє контракт утиліти, а не пунктуацію.

Автор відповідає посиланням на **новий окремий коміт** і результат перевірки.
Після цього закриває обговорення. Якщо не погоджується — наводить команду,
документований контракт або результат тесту; мовчазне закриття не підходить.

Справжні приклади цієї роботи: зауваження Copilot у
[PR #1](https://github.com/w1xes/team-devops-handbook/pull/1)
про глобальні хуки й verbose-коміти та окремі виправлення з регресійними тестами.
Автоматична перевірка і рев'ю Copilot не означають незалежного людського
схвалення й не доводять виконання вимоги «кожен учасник рецензує іншого».
